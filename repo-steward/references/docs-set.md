# docs 四件套的职责边界

README 保持精简，其余说明由 `docs/` 四篇承担。四篇各自回答一个问题，避免互相复制。

## 何时启用

- README 超过约 120 行，或开始出现架构、构建、API 细节。
- 有多类读者（使用者 / 开发者 / 维护者）。
- 构建、部署、发布流程需要成文。
- 项目有对外 API、CLI、配置格式或数据 schema。

README 足以承载全部说明的项目（个人博客、小型工具）可以不设 docs，在 `AGENTS.md` 记录“刻意缺失”。

## 四篇分工

| 文件 | 回答的问题 | 写什么 | 不写什么 |
| --- | --- | --- | --- |
| `architecture.md` | 系统由什么组成？ | 组成、分层、数据流、边界、不变量、目录职责 | 为什么这样选（放 design）、命令（放 development）、API 列表（放 reference） |
| `development.md` | 我怎么开发、构建、测试？ | 环境要求、首次启动、构建、测试与门禁、常用命令、扩展点 | 架构论证、API 全量清单 |
| `design.md` | 为什么这样设计？ | 设计约束、关键选择、权衡、被否决的方案 | 当前 API/配置细节、操作步骤 |
| `reference.md` | 具体怎么调用、配置？ | CLI 用法、参数、API 结构、JSON Schema、文件格式、错误码 | 教程式叙述、架构动机 |

## 写法约定

- 每篇一个主题，标题层级不超过三级；首段给结论，再展开。
- 代码块标注语言；命令可直接复制。
- 路径、参数、字段名使用反引号。
- 版本用 `vX.Y.Z`，日期用 `YYYY-MM-DD`。
- 引用其他文档用相对链接，不复制整段内容。

## 单一事实源

- 一个事实只写在一个地方。README 只做路由，细节放 docs。
- 同一内容若同时服务项目与 agent skill：以 skill 的 `references/` 为 canonical，项目 docs 链接过去，不手写副本。
- 自动生成的副本必须可校验；无法校验的副本不保留。

## 与维护钩子的关系

`AGENTS.md` 中的钩子应指向这四篇，而不是复述内容。例如：

- 功能/行为变更 → `architecture.md` 或 `design.md`。
- 构建/测试流程变更 → `development.md`。
- CLI/参数/API/Schema 变更 → `reference.md`。
